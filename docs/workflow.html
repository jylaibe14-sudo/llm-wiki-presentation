WORKFLOW / GRAPH & REFLECTION

從讀資料到產生課件：可重複、可檢查

本實作的 raw/ → wiki/ → docs/ 是有版本、有引用對應的資料流。LLM 協助將經查核的資料轉成摘要與教學內容；本機程式負責可重現的產出與結構檢查，沒有假稱使用自動 LLM API。

NODE 01取得資料核對 6 份原始論文／設計文件書目與摘要
NODE 02Ingest Wikiraw JSON → 6 篇來源頁＋7 篇概念頁
NODE 03查詢與整理找概念與相關來源，設計初學者教學順序
NODE 04檢查來源 ID、頁面引用、Wiki 關聯與資料限制
NODE 05生成 HTML14 頁可操作簡報與 Wiki 網站
NODE 06瀏覽器檢查／發佈鍵盤切換、互動小測驗、手機版面；全通過才部署
↶ Loop A：若來源摘要缺少限制或關聯頁有問題，回到「取得資料／Ingest Wiki」修正。
↶ Loop B：若簡報引用不存在、敘述不符來源，回到「查詢與整理」修正，重跑檢查後才能輸出。
↶ Loop C：若手機寬度溢出或互動失效，回到「生成 HTML」修正，再測試才能發佈。

每個節點要做什麼？

  1. 取得資料：核對作者、年份、URL；保存重要主張與適用限制。
  2. Ingest：產生來源筆記、概念頁、索引及互相連結。
  3. 查詢：先讀 Wiki 中的已整理重點，再選入 14 頁教學結構。
  4. 檢查：驗證投影片引用的 S01–S06 都存在、概念頁與相關連結正常。
  5. 生成：由同一份 JSON 資料輸出可直接瀏覽的靜態 HTML。
  6. 瀏覽器測試：桌機與手機檢查版面，試按翻頁和小測驗。

為什麼這樣設計？

把「來源檢查」放在生成前，避免簡報完成後才發現說法沒有根據；把 Wiki 當成中介層，讓新增論文後可以更新既有主題，而不用重做整套課件。

產生網頁後還需執行一次實際瀏覽器檢查，避免 HTML／JavaScript 正確性問題。來源完整性檢查不等同所有研究結論都已被形式化驗證。

關鍵原則：可追溯、可更新、出錯時能退回前一節點。

反思：最容易出錯的是哪個節點？

最容易出問題的節點是簡報生成與版面檢查。第一次在 390px 手機畫面測試時，發現底部翻頁按鈕把網頁撐到 438px；修正 footer 的彈性排版後，重新量測符合畫面寬度。此外，從多篇論文濃縮教學內容也容易漏掉來源 ID，因此用故障注入測試檢查器。

另以「RAG 忠實度」為例：一個回答即使忠於舊規定，也不保證符合最新政策，因此內容中額外標註資料適用限制。

修改了哪裡？

原本容易在簡報輸出後才人工回頭核對，現在改成在 Node 01 來源入庫前 要求填寫「來源限制」欄位，並於 Node 04 生成之前 逐頁強制檢查引用 ID；另新增 Node 06 手機及互動測試作為部署前關卡。

加入自動引用存在性測試，模擬故障 S99 能被擋下；也把手機超出寬度列為檢查項目。兩項都通過才部署，讓來源錯誤與排版錯誤能在公開前被發現。
